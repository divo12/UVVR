UVVR skill work roadmap

A learning-gated construction plan for turning the unverifiable-to-verifiable research into a compact AI-agent skill, validating it on real tasks, and only then packaging it as a Codex plugin.

1. Objective and boundaries

Build a skill that helps an AI-product team convert a fuzzy task into the strongest feasible eval package: deterministic gates, observable outcomes, independent anchors, calibrated semantic proxies, and an explicit unverifiable remainder.

Primary user

An engineer, researcher, or product owner who knows what their AI system should accomplish but does not yet know how to turn that intent into defensible evals.

Core job

Input:  task description + examples + risks + available evidence

UVVR:   decompose intent
        route criteria to V4/V3/V2/V1/V0
        propose task transformations
        specify eval cases and graders
        validate the graders

Output: eval contract + verification ledger + unresolved remainder

Must do

  • Separate verification from proxy judgment.
  • Prefer external evidence and execution.
  • Expose grader blind spots.
  • Generate actionable eval artifacts.

Must not claim

  • Universal objective truth.
  • Automatic verification of taste or ethics.
  • That an LLM judge is ground truth.
  • That a high score proves deployment safety.

Explicit non-goals for the first version

  • No hosted eval platform.
  • No database or dashboard.
  • No MCP server.
  • No always-on lifecycle hooks or persistent modes.
  • No support for every agent host.
  • No automatic execution of untrusted generated grader code.

3. Target product shape

The skill should behave like an interactive eval architect. It asks only for missing information that materially changes the eval design, then emits a standard artifact.

Required workflow inside the skill

  1. Capture intended outcomes, failure examples, forbidden outcomes, and available evidence.
  2. Decompose vague quality into atomic criteria.
  3. Route every criterion through the V4→V0 ladder.
  4. Suggest transformations for criteria that cannot be checked directly.
  5. Generate normal, negative, boundary, adversarial, counterfactual, invariance, and OOD cases.
  6. Define grader calibration with known-good, known-bad, valid-alternative, and exploit outputs.
  7. Produce a verification ledger rather than one opaque score.

6. Construction steps

Each step is scoped so a fresh coding agent can execute it without needing hidden history.

1

Freeze the product contract

Depends on: L0 · Mode: docs-only · Rollback: delete the draft
ContextUVVR must turn fuzzy AI work into an honest eval design, not automatically declare subjective work verifiable.
TasksFix the first wedge as research agents. Finalize vocabulary, V4–V0 ladder, output contract, non-goals, and four research-focused before/after examples: source QA, literature survey, decision brief, and deep-research report.
ArtifactsREADME.md, docs/product-contract.md, four concise files under examples/. Keep the existing research report and study HTML at their current root paths for MVP.
VerificationA new reader can classify each example, identify its residual blind spot, and explain why no model judge is called ground truth.
Exit criteriaResearch agents are the single declared wedge; all examples use the same output vocabulary; no runtime feature is required.
Do not addManifest, hooks, modes, CLI, MCP, database, or multi-host adapters.
2

Create the instruction-only MVP skill

Depends on: Step 1 + L1 · Mode: one skill · Rollback: revert one directory
ContextPonytail's true MVP was one skill plus examples. UVVR should first prove that a compact instruction artifact changes agent behavior.
TasksWrite skills/uvvr/SKILL.md with triggers, interview rules, ladder, transformations, grader-validation requirements, output template, and explicit boundaries.
ArtifactsOne skill file, ideally under 180 lines; no duplicated rule mirrors.
VerificationRun five hand-authored prompts. Confirm the skill asks only material questions and produces criterion maps with explicit V-levels and blind spots.
Exit criteriaFive complete outputs; zero cases where an LLM score is mislabeled as verified; instructions fit in one readable file.
RollbackReturn to the product contract and examples if the skill requires long explanations to remain coherent.
3

Dogfood on real AI-system tasks

Depends on: Step 2 + L2 · Mode: evidence collection · Rollback: none; preserve failures
ContextSynthetic examples can make any prompt look good. The skill needs messy tasks with missing evidence, conflicting goals, and real constraints.
TasksRun six cases: three research-agent tasks, one impossible/V0-heavy research task, one customer-support out-of-domain contrast, and one safety-sensitive research task. Blind-review baseline and UVVR outputs.
Artifactsdogfood/cases/, sanitized inputs, UVVR outputs, dogfood/review-checklist.md, shuffled anonymous output IDs, reviewer notes, and failure taxonomy.
VerificationReviewers score shuffled outputs without knowing baseline versus UVVR. Each failure is assigned to interview, decomposition, routing, transformation, grader design, or reporting—not patched with an unrelated rule.
Exit criteriaAt least two recurring failure patterns discovered; at least one correct V0 preservation; review checklist and anonymization procedure are reproducible by another person.
RollbackNever delete bad outputs. They become the regression corpus for later steps.
4

Harden the workflow and artifact schema

Depends on: Step 3 + L3 · Mode: skill refinement · Rollback: version skill revisions
ContextOnly repeated dogfood failures justify new rules. The output should become stable enough to compare across runs and systems.
TasksRevise the skill, define a minimal JSON/YAML criterion schema, add release-gate semantics, confidence, false-positive tolerance, provenance, and unresolved-risk fields.
ArtifactsSkill v2, schemas/eval-contract.schema.json only if needed, regression examples, changelog explaining every new rule.
VerificationOld failure cases now pass without regressing successful cases. Validate schema with the platform standard library where possible.
Exit criteriaStable output contract across ten cases; every field has a consumer; no speculative configuration.
RollbackRemove fields that do not change a decision, grader, or report.
5

Build the benchmark and grader self-tests

Depends on: Step 4 + L3/L4 · Mode: executable evidence · Rollback: preserve raw workspaces
ContextThe benchmark must be able to disprove UVVR's value. Compare the same agent with and without the skill on real eval-design tasks.
TasksCreate treatment/control arms, frozen task corpus, deterministic checks for structure and honesty, calibrated model judge only for residual quality, repeated trials, offline rescoring, and explicit evaluator trust boundaries.
Artifactsbenchmarks/, task definitions, good/bad references, self-tests, preserved run outputs, published limitations.
VerificationGood reference passes; plausible bad reference fails; judge ranks complete/honest contracts above flattering but invalid ones; treatment does not leak into control. Evaluated runs cannot read hidden references/holdouts or write graders, logs, or benchmark assets.
Exit criteriaSelf-tests pass before model spend; benchmark reports variance and negative results; verified metrics remain separate from judge scores.
RollbackRescore preserved artifacts after grader changes; do not regenerate expensive runs unless behavior changes.

Benchmark integrity invariants

  • Control prompt text is frozen, reviewed once, and contains no UVVR vocabulary.
  • Treatment and control run in fresh isolated directories with identical tools and permissions.
  • Hidden references and holdouts are outside evaluated agents' readable paths.
  • Graders, benchmark assets, reward calculations, and run logs are read-only to evaluated agents.
  • Deterministic checks run before any semantic judge.
  • The judge model family differs from the evaluated model family when practical; disagreements remain visible.
  • Generated executable grader code is sandboxed or excluded from MVP.
6

Run an external instruction-only pilot

Depends on: Step 5 + L5 · Mode: external learning · Rollback: keep skill private
ContextThe first outside signal must arrive before companion skills or portability work. Pilot users can copy the one skill directory manually.
TasksRecruit two or three users working on research-agent evals. Give them the skill and study guide, not benchmark answers. Compare their manual and UVVR-assisted designs.
ArtifactsPilot protocol, anonymized tasks, blind review scores, interviews, disagreements, and a decision record on whether the core job is valuable.
VerificationUse held-out tasks absent from examples and benchmark development. External reviewers can reproduce the verification ledger and identify its unresolved remainder.
Exit criteriaAt least two users complete the workflow; independent review finds a material improvement or the project records a falsifying result.
RollbackIf the workflow does not help, revise or stop before creating plugin surface area.
7

Package the externally validated skill for Codex

Depends on: Step 6 · Mode: packaging · Parallel with optional Step 8
ContextPackaging begins only after instruction behavior and external value are stable. Codex can load skills directly; UVVR does not need always-on context.
TasksAdd the minimal .codex-plugin/plugin.json, metadata, license, install instructions, and plugin validation tests.
ArtifactsCodex manifest pointing to ./skills/; no hooks unless a demonstrated failure requires them.
VerificationInstall from a clean checkout, discover and invoke the skill, uninstall cleanly, and confirm no filesystem state is left behind.
Exit criteriaOne-command install works; packaged behavior matches pilot and benchmark behavior.
RollbackUsers can continue copying the single skill directory manually.
8

Add only pilot-proven companions and portability

Depends on: Step 6; packaging lane may run in parallel · Mode: optional growth
ContextSeparate operations and new hosts exist only if pilot sessions reveal distinct repeated jobs or installation demand.
TasksFirst candidate is uvvr-audit, but build it only if multiple pilot sessions require auditing existing evals. Add another host only when a pilot user requests it.
ArtifactsOne small skill per proven job, behavior tests, and a decision record for every adapter or runtime feature.
VerificationEach companion has distinct triggers and outputs, reduces core-skill complexity, and does not mutate files unless requested.
Exit criteriaEvery addition maps to repeated external usage; otherwise this step is explicitly skipped.
RollbackRemove weak companions and remain Codex-only.

7. Benchmark strategy

The benchmark's unit is not prose quality. It is whether the skill produces a more complete, honest, and operationally useful eval design.

Arms

  • Baseline agent with no UVVR guidance.
  • Short generic prompt: “make this task verifiable.”
  • UVVR skill.
  • Optional expert-authored reference, excluded from the model comparison.

Task families

  • Source-grounded question answering.
  • Literature survey.
  • Comparative decision brief.
  • Long-form deep-research report.
  • Impossible or heavily V0 research request.
  • One customer-support out-of-domain contrast.
  • One safety-sensitive research task with non-negotiable gates.

Metrics

MetricTypeWhat it prevents
All criteria assigned a V-levelDeterministicUnclassified or silently subjective requirements.
Blind spot named for V0–V2 criteriaDeterministicOverclaiming certainty.
Hard failures encoded as gatesDeterministic/referenceAveraging away safety or permission failures.
False-positive calibration designedStructuredTrusting an untested grader.
Original-task holdout retainedDeterministicProxy-task transfer claims without evidence.
Operational completenessCalibrated judge/expertBeautiful framework with no runnable eval cases.
Intent fidelityExpert/humanOptimizing checkability while losing the user's goal.
Benchmark invariant: a shorter or more “verifiable-looking” output cannot win if it omits the intended outcome, treats a judge as an oracle, or fails to include a grader-validation path.

9. Anti-pattern catalog

Building a universal eval platform before one skill works

The first proof is behavioral: does a compact skill reliably improve eval design? Infrastructure cannot answer that.

One aggregate “verifiability score”

Keep verified, anchored, proxy, and human-only coverage separate. Aggregation hides which guarantees are real.

Calling LLM-as-judge verification

It is a structured semantic proxy. Require calibration, evidence, independent holdout, and an explicit unverifiable option.

Generating only synthetic happy-path tasks

Real production work contains conflicting criteria, missing evidence, impossible requests, policy constraints, and delayed outcomes.

Optimizing directly on public examples

Examples teach the workflow; hidden benchmark cases measure generalization. Do not use the same artifacts for both.

Self-grading with the same model and prompt family

Correlated errors produce false confidence. Use deterministic checks first, cross-family judges, and human calibration.

Adding hooks because Ponytail has hooks

Ponytail is an always-on mode. UVVR is an invoked construction workflow. Packaging should follow behavior.

Duplicating the rule text across hosts too early

Mirrors create drift tests and maintenance. Keep one source of truth until portability is demanded.

11. Plan mutation protocol

This roadmap should change when evidence changes. Record every mutation in a short decision log.

  • Split a step when it has two independently verifiable outcomes or conflicting file ownership.
  • Insert a step only when a newly discovered dependency blocks the next exit criterion.
  • Skip a step when its user need disappears; record the evidence, not “out of time.”
  • Reorder steps only if all dependency edges remain satisfied.
  • Abandon a feature when dogfood or the benchmark shows no value; preserve the result as evidence.
  • Reject scope expansion when it solves a future distribution problem rather than the current skill behavior.

12. The first decision—not the first code

Before Step 1, choose one initial wedge. The skill can generalize later, but examples and benchmarks need a concrete starting domain.

Research agents

Richest demonstration of claims, evidence, coverage, synthesis, source quality, and unverifiable judgment.

Customer support

Strongest demonstration of external state, permissions, safety gates, policy, and communication quality.

Coding agents

Most naturally verifiable, but may underrepresent the difficult open-ended problem UVVR exists to solve.

General assistants

Broadest market, but too diffuse for a clean first benchmark.

Decision: start with research agents. Use customer support only as the single out-of-domain contrast during dogfood. This preserves one coherent MVP while checking that the ladder is not merely a research-specific rubric.

Once this choice is understood and accepted, Step 1 can begin. Until then, the correct output is this plan—not a scaffold.
